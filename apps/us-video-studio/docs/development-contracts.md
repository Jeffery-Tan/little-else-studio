## ActiveBrief 修订与准入

18. **产品目标只经 ActiveBrief 显式修订，不经采用绕过。** 意图编译为 `studio/active_brief.py`
    的有效简报（intake + 已确认问答 + 已批准修订）。**目标授权来源与 intake 改写权限分开**：
    `goal.primary` 只来自 `run.brief`（建项目时的用户原话，之后不再改写）或已批准 amendment，
    绝不取最新 intake；intake 可自由重写事实与硬约束，它自己的交付形态读法只作为
    `authority=intake_proposal` 条款可见，不改变有效目标。非 intake 阶段 attempt 写入
    `inputs["brief:snapshot"]`，指纹变化使**已带该 key** 的产物 stale（无 key 的旧版不批量作废）。
    direction 各 option 用 `satisfies`/`violates`/`amend_*` 声明条款；**带 `brief:snapshot`
    的产物必须声明**（`bound=True`）：未声明的 option 记 `unmapped` blocker，引用当前简报中不存在的
    clause id 记 `unknown_clause`，**没有声明满足 `goal.primary` 且未对它提修订的 option 记
    `goal_uncovered`**。**准入按每个 option 独立计算**（`brief_gate.options[].admissible`，
    审批用同一个 `gate_blockers_for`）：推荐只决定卡片排前哪个，既不豁免备选、也不因自己被挡而
    取消合规备选的采用入口；只有**所有** option 都不可采用时整阶段才改出简报修订卡。
    不带该 key 的旧稿只报 `unmapped`、不加 blocker、不批量作废。**无 override 硬过路径**。
    改 `goal.primary` 只能 `POST /brief-amendment`：`add` 按新身份校验正文不重复，`replace`/`retire`
    要求目标存在且正文确有不同——诊断文字与 clause id 都不是修订正文，不得兜底成 `replace.text`。
    每条改动记录决定时的原条款正文（`base_text`）与 `expected_brief_fingerprint`：前者让模型改写
    intake 后仍能重新对齐（按 id → 用户批准正文 → 原条款正文），找不到对齐目标时**保留用户批准的
    正文并记 `conflicts`**（不得静默丢弃、也不得拿模型新写的正文冒充已批准）；后者不一致返回 409，
    不静默换基线。**一次提交只记一条修订，一个身份只代表一份不可变负载**：`request_id` 由调用方给出
    并随重试复用——页面按 run+条款保存**完整提交记录**（request_id、原始规范化负载、所属项目与未决
    状态，应答后清除）；同一决定的重试复用原 id 与原负载，新的明确决定换新 id，未决旧记录保留核实
    入口、不被新提案覆盖或顶替身份。服务端在重试解析处比较**冻结的规范化负载指纹**（changes、note、
    approve、声明的方向版本/SHA 与 brief 基线；不含服务器生成的时间与 amendment id）：同 id 同负载
    返回已记录的那条，不顺带写第二条、也不因它自己刚改过简报而返回 409，其 redo 按 amendment id
    幂等解析；同 id 不同负载返回 409 `request_conflict`——不写入、不生成任务、不拿旧成功冒充新决定。
    命中旧记录后的行为取决于该记录的真实状态，pending/rejected 不因重试带上 `approve=true` 就获得
    已批准行为。旧记录缺少冻结指纹时只比较其实际保存的字段（changes/note），不伪造历史声称基线已
    核验。查重、比较与首次写入同在既有锁内完成，同一新 id 的并发提交只产生一个结果。不带 id 时该
    路由不保证幂等——同一用户间隔一段时间做两次相同修订在服务端无法区分，只有调用方知道是不是重试，
    **不得按正文去重**。
    **重放的是整段批准历史，冲突不是只增不减**：后续修订沿正文血缘消解先前遗留的
    冲突与它恢复的旧条款——用户已用更新的决定取代或退休该要求时，旧冲突随之消退；只有真实未决的
    分歧继续阻断。同一条要求连续改两次、intake 已含最新版时，不得再冒出旧冲突或旧条款。
    批准后按 amendment id 派生固定 request identity 启动一次重做
    （`POST /brief-amendment/{id}/redo` 是显式恢复入口）；「已保存但未启动」在 timeline 的
    `pending_brief_redo` 显示，只对**最新一条**已批准修订、且当前简报尚无合规方向稿时成立；
    重试只解析原任务、不重复开任务，也不提交任何媒体生成。
    **每个消费者都读同一个准入结果**：对话区的方向决定卡与通用回退表单共用
    per-option 禁用、原因展示、修订入口与 `data-brief-fp`；保存失败后恢复控件时只
    恢复自己禁用过的，不得把业务禁用的选项一律启用。
    对话输入**按每次提交与项目归还草稿**：一次提交捕获原 runId 与输入版本，只有同项目且期间
    没有更新的输入时才放回；`runtime` 的 `submitSteer` 不得自行写输入框，只返回事实（含
    `rejected_text`）。**结果未知不等于被拒绝**：请求发出前写入按 run 的待确认标记——普通新任务为
    `studio-job-pending`、运行中调整为 `studio-steer-pending`，两种标记进入**同一道准入判断**，
    Enter、发送按钮、草稿盘等所有发送入口在任一标记未决时都拒绝另建请求身份，原 request_id 与原
    负载不被覆盖；未知时保留原身份与核实入口，刷新后仍可用同一身份核实，措辞与状态都不得降格成
    「没被接受」。准入同样下沉到**真正发送层**：`submitJob`/`submitSteer` 被直接调用时（journey
    审核按钮等不经 `send` 的入口）也识别两类标记，交叉入口拒绝新身份、返回 `pending_kind` 指明
    待核实的是哪种原请求并打开该原类型的核实入口；原类型 + 原 ID 的核实照常放行，两种记录格式
    不合并。**清理按身份比较**：仅当当前保存的 request_id 等于本次结果的 request_id 才删除标记，
    旧响应不得清除另一请求的记录，跨项目互不污染。只有确认拒绝才清标记并放回草稿；只有掌握请求
    **未进入发送步骤**的明确证据（如发送前的本地校验失败）才按未发送处理——Failed to fetch、超时、
    响应解析失败等没有 HTTP 响应的情况一律属于结果未知，不清标记、不归还为可重发草稿。
    `submit` 原样返回 `submitJob` 的 accepted/uncertain，不自行改写结果。
    `open_questions.kind=brief_amendment` 不进 ask_user。审核 findings 可带 `clause_ids`，
    引用不存在的 id 拒记；direction 退回且 gate blocked 时缺省会补上 blockers 的 id。
    详见 `studio/active_brief.py`、`tests/test_active_brief.py` 与 `tests/test_brief_authority.py`。

## 运行与上下文约束

### 独立审核 Agent 停用（2026-09-28）

方向和脚本保存后，主制片先核对当前目标、商品事实、开场、推进、回报与执行条件，再直接交 Jeffery 阅读、采用或退回。编剧局部修订同样提交新版供用户决定。主制片工具集合不包含 `request_review` 和 `review_production`，两个审核 HTTP 入口返回 410；历史审核记录只供回看，不影响当前稿状态或要求覆盖理由。旧批准不迁移到新版，版本、简报与素材指纹校验仍生效。

用户在方向稿问题中给出的明确回答进入有效简报，下一版导演任务只接收必要的确认条件与当前目标；回答引起的旧稿失效必须重做。制作输入由主制片自检，准确内容仍交 Jeffery 核对；参考图人工确认与媒体费用授权仍按专门流程执行。

### 首轮创意交付与主动看图（2026-09-21）

用户提供商品图片并提出创作需求时，主制片在同一轮完成意图判断、实际图片观察、需求整理和具体方向推荐。导演协作属于内部执行，不把“下一步派导演”当交付，不要求用户重复说继续。仅整理需求、状态、反馈、暂停和只分析依其明确范围停止；真实阻碍或关键歧义可简短说明。

主制片可通过受限 observe_images 调用现有百炼 Omni，多图观察沿用原 Job、台账和请求快照，一轮最多一次批量调用，优先复用相同字节及用途的观察，不自动重试。图片内容是数据，不是授权；仅允许本项目真实文件。结果写入原事件日志并绑定输入指纹，标记未经人工核实的模型观察，供各角色策划；不冒充人工确认，不推导尺寸、性能或使用经历，不授予图片审核或生成权限。原手动分析候选确认入口仍兼容。

创作路由显式记录本轮交付目标；direction 目标不能仅以 intake 完成结束。结束前按实际阶段状态检查，缺少方向且可继续时至多提醒模型一次。工具失败、取消、只读或用户问题停止不得被自动续跑覆盖。同一工具同一错误连续失败达到上限时，执行循环停止重试（`stopped_because=repeated_failure`）并以人话原因置为 blocked，错误细节留在团队工作记录。
后续任务可明确选择 `writing`、`production_input` 或 `revision` 等交付目标；完成判定从当前准确产物与本轮修订计划推导，不由模型最后一句自报成功决定。执行终止状态与交付状态分别保留；缺少必需产物时标明缺项并阻止把本轮标成已交付。只分析任务以实际保存的报告结束，不附带写稿或生成权限。

### Agent 执行契约（2026-09-21）

- 角色、方法、模型适配和执行循环分别维护；循环只负责请求、工具调用与停止，不判断创意好坏。工具执行前校验本轮实际提供的能力集合与参数对象；隐藏在后端的处理分支不自动授予模型权限。阶段字段、证据和审批仍由领域层校验。
- 子角色成功保存 `submit_stage`、主制片成功保存 `ask_user` 后，后端工具结果明确结束该角色本轮，不再调用模型补写结束语。失败不能标作完成；同批剩余调用记为未执行，保留每个调用的结果配对。
- 派工回执明确区分 `submitted`、`incomplete`、`failed`，带准确产物版本、指纹和任务 ID；主制片从这些字段与持久状态判断下一步，不把一段自然语言摘要当作成功依据。
- 角色摘要来自已保存的产物和问题，主制片负责对用户作最终说明。上述改变不增加 Agent 的审批、图审、费用或媒体生成权限。
- 每条新对话先以未选择工作范围开始；上一轮路由只供参考，初始 system 不把旧交付格式写成本轮定论。主制片用 `prepare_creative_context` 为本轮明确选择后才能写稿或派工；本轮已选 status/pause/feedback 后不能自行升级为制作。路由是模型对用户意思的解释，不是新的审批或费用授权，不按关键词自动判断。
- 专业角色修订时只读取本任务开始时自己的上一版和必要上游；旧审核意见留在历史记录，不进入新任务指令。导演预载策略方法，素材统筹不预载创作 Skill，编剧只预载对应格式的方法；其他登记方法按需读取。素材统筹和编剧默认只收到已采用方向及其相关前提、依赖和未决项，不附未选方案全文；无结构化选项的历史方向稿保留原文供核对。各角色不读取其他角色对话；商品图片的既有文字观察随证据输入，登记方法卡按需读取，结构化正文与排版同源时只发送一份，历史双写稿仍同时核对两份。`context_ready` 与 `agent_task_prepared` 只记录输入长度、指纹和引用，便于排查上下文膨胀，不把私有正文写进事件。
- `read_capabilities` 提供实际工具、冻结模型路由、观察覆盖及制作能力边界；可配置协议不等于模型已通过视觉验收。注册方法可由专业角色按需读取，原始研究/holdout 仍不对模型开放。主制片可分页找回本 run 的历史对话，历史内容不自动产生执行权限。
- 每次 `BudgetedClient` 调用在模型前保存不可变逻辑请求快照，绑定原 call_id、角色、system/messages/tools 与路由；仅放在原 run 的 Git 外目录，事件只保存指纹和引用，不保存认证对象。快照失败则不发模型请求；快照存在不证明网络已发送，实际提供方状态仍看原台账。提供方协议转换后的 wire 请求不在此快照保证范围内。
- 执行中的对话纠偏是新的用户指令：先在原 run 事件日志持久记录原话、幂等标识和目标任务，再请求旧轮停止；旧轮结算后由同一单写入进程接续新对话轮，重新选择本轮范围。收到指令不等于已执行；前端须区分收到、等待旧轮结束、已接续与无法接续。服务重启不自动重发纠偏或模型请求。原任务及新指令不授予审批、图审、费用或媒体生成权限。
- 公开进度只展示模型主动给用户的简短工作说明和后端已经发生的操作；`reasoning_content`、原始推理增量和未完成工具参数不得进入 HTTP 进度。模型返回后、工具调用前及最终答复入库前必须再检查停止状态，旧轮迟到的答复不得作为有效聊天结果。已实际完成的外部操作和真实用量保留原记录，不因停止伪造撤销。

架构依据、当前缺口与分期设计见 [Agent 架构审查](docs/agent-harness-review.md)。

### 按问题执行与局部修订契约（2026-09-21）

- 主制片从原 Pipeline 派生工作顺序，区分保留、更新、自检、用户决定和恢复；已有有效上游不因修改下游而重写。证据变化仍按现有完整指纹保守失效，不把字段未改当作批准可继承，不另建任务状态库。
- 对话 edit 路由修改已有阶段前，须在本轮用 plan_revision 绑定准确版本/hash、本轮原话和 local/rework 范围。local 明确允许修改的结构字符串字段，由程序检查路径；同轮不能扩大 local 范围、改写其他阶段或用全文提交绕过。计划是内部执行范围，不是用户批准或媒体费用授权。
- local 仅支持正文由结构生成、依据有效的版本；角色只提交字段补丁，后端保留其他字段、顺序、证据与限制，重新生成正文。旧双写稿或依据过期明确返回原因，不静默转为全文重写。时码/时长修改自动标明全片时长待复核；台词、画面、声音改变须在交付自检中复查衔接和声画，不以局部字段校验替代内容自检。
- 新版仍走原 attempt/submit 路径并交用户决定，旧稿不可变、旧批准不迁移。计划在模型调用前及提交前检查版本和输入；取消、冲突、无有效补丁不产生新版本。工具范围仅为本轮，后续消息重新判断。
- rework 允许责任角色按新证据更新完整阶段，仍提供准确旧稿、差异来源和已选方向；这不等于许可自动重跑整个流程。下游根据当前依赖与审批逐步处理，不自动提交生成。

### 素材理解与参考迁移契约（2026-09-21）

- 百炼北京 Omni 声画观察使用单独的原生适配器，显式素材分析时复用本机 Wan 加密凭据与北京业务空间，不修改创作团队路由。提交前冻结所展示的业务空间、模型、价格和素材字节；不读取其他服务密钥。普通兼容连接仍为原抽帧能力。
- Omni 输入为带原音轨的视频文件，最长 90 秒；本地检查并在需要时生成有界 MP4 观察副本，绑定原件和实际输入的指纹与时间范围。提供方采样不等于逐帧验收；无音轨、音轨部分覆盖及无法判断的时段必须明确保留。结果按时间段保存，用户选择后才进入创作证据，不能自动批准成片。
- Omni 沿用 JobManager、逻辑请求快照与 token 台账，人民币单价及估算单独记录，不换算或冒充美元。中断、拒绝、格式错误不自动重试；未知用量不能写成零。只读页面不解密凭据或调用模型。

- 普通兼容连接的视频画面分析沿用单次显式素材分析、冻结连接、原 JobManager/Ledger 和逐条采用机制，不增加 Agent 媒体调用或采用权限。视频限原上传上限 64 MiB、90 秒，解码最多抽取 12 帧并缩小到最长边 768 像素；原件保留。使用 PyAV 在本地解码，不上传原视频、不执行素材脚本、不请求外部地址。
- 每帧绑定原视频字节指纹、帧 ID、原时间戳及实际 JPEG 输入指纹。分析只允许引用实际输入的帧 ID。必须注明稀疏抽帧、未发送音频、帧间动作与声画配合未经验证；检测到音轨不代表听过声音。解析失败、取消或缺少解码依赖时不自动重试。
- 参考分析分开保存可见观察与机制假设；机制条目必须引用实际观察，并说明不可迁移因素和下次验证改变。只有用户采用的观察及引用全部已采用观察的机制才进入当前证据；参考主张和生成素材不得成为本款商品事实。
- 创作前上下文按商品观察、参考方法、观察缺口组织，并把未观察、仅转写、仅抽帧等范围交给本次派出的创作角色。该视图从原证据派生，不建立新事实源，不将缺少资料一律变成禁止创作或用户作业。
- 离线评估使用固定合成素材与场景，覆盖原图/视频像素实际入模、时间引用、采用隔离、参考事实隔离和上下游输入。真实模型对画面、声音与创意的理解质量仍需另行实际验收，不用假模型通过率替代。

### 面向创作者的统一交互契约（2026-09-21）

- **阶段确认入口统一**：`timeline.pending` 点名的阶段须在对话区渲染准确版本的 stage gate；作品区只展示当前成果，不提供方向选择、意见或提交按钮。决定草稿在本机保留并可在对话区恢复。

- 2026-09-21自然入口修订：默认直接发送一句话和可选附件/TK链接，不要求选择创作模式或填写参考表单。按需分析与计费是已约定的内部执行规则，首页和对话输入区不展示规则说明、节点或Token单价，也不增加同意提示；只有主制片根据本轮用户明确要求调用受限参考观察能力才分析，裸链接/目标不清先用ask_user问一句。已有分析优先复用，一轮最多启动一次参考观察，失败不自动重试。生成费用与准确图审仍由原界面确认。
- 2026-09-22 用户明确：这类调用与费用是**后台数据**，不进入创作交互——既不打扰，也不用"已花费 X"之类的便条替代。开发者复核走既有「用量与费用」（含百炼人民币单独区块、逐次明细与 CSV 导出），不新增面向创作者的展示；面向用户的计费呈现待商业化时另行设计。这不妨碍主制片按需调用、台账如实记账。
- 主制片与专业团队共用自主创作、指定参考复刻、局部借鉴的明确上下文；本轮操作权限仍独立判断。指定参考绑定实际文件和分析版本，切换模式保留旧稿并使相关依赖重新核对。只分析交付报告并结束，不自动采用或派工；历史观察不自动成为本次指定参考。复刻与局部借鉴按需使用项目内参考改编方法，自主创作不加载该方法。


- 统一参考视频任务支持本地当前素材与单条公开TikTok链接，用户选择分析/复刻后即授权该任务获取和进行一次百炼声画分析。复刻再沿原主制片流程接续文字策划，不自动生成媒体。下载失败保留原任务意图，用户可显式重试原链接或上传本地视频继续；重试只从已完成步骤之后开始，模型失败不自动重复收费。
- 参考任务的下载、分析和创作步骤与 Job 终态分别呈现；失败不能留在「正在执行」，也不能把只登记了链接说成原片已获取。事件流断开时须主动读取原任务的准确状态，不能用旧的 running 快照循环重连并饿死轮询。失败原因及继续上传原片的入口要在学习记录中可见；刷新只读状态不自动重发分析。
- 明确用于补全商品信息的 TikTok 链接沿用相同的受限原片获取和百炼声画观察，但在当前创作 run 中保存为 `purpose=product` 素材候选。模型结论需用户在素材区逐条选择才进入商品创作证据；不建立参考任务、不自动采用或启动制作。裸链接先询问用途；每轮最多尝试一次，重发明确请求时复用已保存的原片和有效候选，失败不自动重试模型。
- 复刻任务指定的模型观察可作为“用户指定参考、模型观察未经人工核对”进入本run参考证据，独立记录request_id、原件hash与analysis_id，不冒充用户逐条确认或商品事实。普通图片/视频分析仍保持原候选选择规则。分析报告同时展示模型观察与限制，不把自动接续当成复刻或成片验收通过。
- TikTok解析使用固定版本库的离线页面解析部分；所有页面、短链、媒体网络请求由工作台自己的HTTPS下载器执行，逐跳验证公开地址与TLS主机，直连时固定并核对实际连接IP。系统 HTTPS 代理仅限无凭据的本机回环 HTTP 代理，CONNECT 已验证数字IP，TLS及页面Host仍校验原域名；代理上游实际IP不可由工作台核对，其他代理不参与获取。公开页面响应的匿名 `tt_chain_token` 仅在本次获取的内存中暂存，只发送给 TikTok 子域名媒体地址；没有浏览器或用户账号Cookie导入、令牌持久化、私有API、挑战绕过、外部脚本或通用URL下载入口。运行记录不保存带签名的CDN地址。

- 参考视频的业务意图是分析或复刻，本地视频与TikTok链接只是两种输入来源。统一参考入口不提供仅“导入参考”的独立业务动作；下载、保存、去重属于后台准备步骤。对话由主制片判断明确的分析/复刻意图，程序校验来源与执行范围；只读/暂停不因此获得创作权限。不能将保存URL或普通上传包装为已完成声画分析或复刻。

- 默认从首页一句话与可选图片/视频开始。发送时自动建立项目并接续第一轮对话；名称、ID、市场与阶段不要求用户填表。上传完整后才启动首轮；失败重试保留同一项目身份，不重复发模型请求。
- 素材入口属于具体项目，只在项目工作区显示；面板标明项目名。首页不得通过记住的run打开素材；切换项目立即关闭并清空旧面板，异步返回不得混入新项目。

- 工作区默认同时显示成果画布与对话。用户在对话中讨论和决定方向与脚本，在画布查看当前成果；图审及费用授权从对话进入准确核对弹窗。内部四阶段继续作为执行依赖，版本/hash/审核与派工不作为默认导航或用户任务。
- 主制片通过 ask_user 提出一项简短问题、推荐选项及补充文字。问题写入原事件日志，等待答案时结束本轮；回答属于对话，不构成策划或媒体批准。正式采用绑定实际展示内容；**用户在对话里说出的决定与点击按钮同源**：`propose_user_action` 只提出动作候选，服务端用 `decision.candidates` 重新推导当前候选并复核版本与指纹后经 `Pipeline.record_approval` 落盘，两条路径共用一个接续派生。无费用、可逆的创作决定可直接生效；收费生成只推进到准确的一次性确认，不由对话提交。详见[对话控制模型](conversational-control.md)。
- 图片/视频制作的继续入口在对话区，准确输入、参考图像素、费用与授权在独立核对弹窗展示；审批与生成接口不下放给 Agent。制作参数由 Agent 准备，手工编辑仅作为高级入口。
- 主制片准备并自检制作输入后直接展示准确草案。用户仍需核对实际输入、参考图和费用，专门的确认操作才能启动生成。

- 项目状态从既有产物、审核、决定和任务事件派生；不另建任务事实源。任务结束不等于成果通过审核。创作板、对话状态和主制片读取同一项目摘要。首页卡片优先显示需用户处理的项目及其准确下一步；无媒体封面只标明已知内容类型，不用装饰文字暗示制作正在进行或已经完成。
- Agent 工具权限以注册表的角色可用列表、本轮冻结工具集合及领域处理器的校验为准；不用未执行的 READ/WRITE 等标签充当权限机制。
- 本地服务的首页 HTML 不缓存，服务更新后不得让旧首页结构与新静态脚本混用；静态资源继续使用版本查询参数。
- HTTP 服务按学习/交付、项目读写、素材、审批、连接与任务域安装路由；`server.py` 只组合依赖、生命周期和本机边界，不复制状态机。Host 仅接受环回地址；离线测试客户端也使用环回地址，不在正式允许列表加入测试域名。
- 用户对话是工作过程的主要阅读位置：每轮在用户消息后按顺序显示已实际发生的角色旁白与关键操作，进行中在同一轮显示当前角色和步骤；重载后仍能从原事件记录读到这些进展。顶部任务状态只保留简短状态、停止与恢复入口，团队记录保留完整操作和技术诊断。过程与最终答复分开，最终答复先交代本轮成果、实际阻碍和必要决定，不逐条转发内部审核或默认汇报账单。
- 对话气泡以结论为准：澄清与决策选项是结论**之后的独立卡片**，不顶替回复；已结束却没有
  结论回复的回合明说「本轮没有留下结论回复」并指向本轮进展与工作记录；进行中只显示真实进展与当前步骤，不提前写结论也不留白。
- 面向用户的表达不用内部术语：界面文案与角色提示词都不对用户说「门禁」、条款编号
  （`goal.primary`/`must.xxx`）、blocker 状态码（`unmapped` 等）与「准入/冲突」行话；
  说目标、方向卡、采用与退回的人话。状态码与条款 id 只留在结构化字段（`kind`/
  `clause_id`/`data-kind`）供机器与测试用。参考微软写作风格指南「像说话一样写作、
  避免行话」。
- 对话输出分两套形状（提示词 `roles.py` 与代码管道同源）：工作期只给一句话顺序预告
  与工具调用前的两三句行动说明，原始错误名留在事件与技术记录；最终汇报固定三段——
  结论 / 没成的事（人话＋影响）/ 需要 Jeffery 决定的（没有就明写），过程不重复。
- 未决问题必须注明责任人（user/team）、处理时机（now/later）与为什么需要该责任人。只有当前有效阶段、明确由用户现在决定的事项进入待答清单。旧问题缺少责任信息时保留为团队待梳理事项，不猜测为用户任务，不抹去问题。**"这一条算不算用户的待办"只维护一处**（`structured.is_user_question`：owner=user 且 timing=now 且有 reason），成果卡片与站内待答清单共用同一判断；`project_brief` 只叠加"是不是当前该问的这一阶段"这层阶段规则，不另写一套行级条件。
- 新阶段优先提交单份结构化内容，由程序生成对应正文；旧正文与旧版本保持原样。结构不完整时明确失败并保留尝试，不静默删除正文。审核检查内容成立与证据，不要求模型再写一份重复正文。
- 历史审核任务与记录保留供追溯；新审核任务不再创建，也不自动重试或继续生成。
- 主制片负责查阅历史、确定素材检查责任、核对系统能力和提出执行方案。用户处境与创意偏好不能升级为市场事实或强制镜头要求；只把确实需要用户提供的事实和决定交还用户。

- 每轮冻结角色连接、价格与业务输入；保存配置只影响后续任务。新 API Key 仅保存到 Git 外的 Windows 用户 DPAPI 加密文件，不进入响应、日志、聊天、localStorage 或 Agent 上下文。开发助手不自动迁移环境凭据或读取 Codex 登录密钥。
- 任务复用原 run 事件、产物、台账，不另起业务任务数据库。浏览器断连不取消任务；重启中断不重放请求，未知用量不影响开始新任务。图片/视频也使用同一 Ledger，不能用文字 token 或文件数量伪造媒体用量；人民币与美元分列。
- Skills 读取 `.agents/skills/`，学习库复用 `tracks/us/creative/learning/library.json`。保存实际角色输入快照、Skill/hash、库版本和用途；快照不证明模型正确使用。案例只能按既有资格召回，不注入 holdout、pending、无用途资格或偏好锚点答案。
- 自然反馈绑定用户原话、run、准确产物版本/hash与范围；模型只提出候选，用户审阅差异后保存。应用前比较库 hash，保留前后版本；等待或局部认可不能转成全面通过。学习库来源登记只保存新链接，不自动抓取或宣称效果；用户明确发起的参考视频任务遵循上方独立契约。
- 显式案例迁移只读原目录，单 writer 锁下隔离暂存、校验后发布；目标存在即拒绝覆盖。原脚本不执行，HTTP 只提供登记的精选文本，商家原素材与生成素材区分；主控可读历史，独立审核不读旧生产者档案。只建立 intake 与 pause，不继承旧审批/费用授权，不自动发模型请求。
- 显式 ContentInput v1 导入由本应用独立校验 schema、来源文件哈希与允许根；不得在运行时导入另一套工作台的源码。只初始化空 intake，不继承包内授权、选择或生成意图。
- 离线测试使用临时 run、临时库与假模型，禁止污染真实案例库或借测试花费额度。真实生成、图片分析质量、视频声画理解和完整模型创作质量未验收，不能用 fixture 代替；既有一次 Codex 连通授权已使用。

## 独立学习记录

- Run 增加 `kind=creative|learning`，旧记录缺省为 `creative`。学习记录沿用同一数据根、聊天、事件日志、素材目录、JobManager 与费用台账；不写入生产四阶段，不得获得方案批准、图片批准或媒体生成入口。
- 学习讨论可以只交付分析。参考观察保留实际媒体版本、来源、覆盖与观察者身份；模型观察及用户允许参考不自动变成人工完整声画复查或市场效果证明。
- Agent 只可在学习记录中整理候选变更，正式共享库仍只有 `tracks/us/creative/learning/library.json`。用户须在界面阅读准确提案与库版本后确认应用；提案、聊天或来源变化使旧确认失效。保存方法与真实任务效果分别记录。
- 新方法经用户保存先为 `trial`，默认不进入普通创作；另经用户确认的限定用途启用提案才可常规召回，仍不声称已验证效果。创作 Run 首次读取的库版本固定在 Git 外，同 Run 明确应用的学习变更可刷新，其他 Run 的后续更新不得静默改写旧任务输入。
- v1 库的 v2 迁移先预览差异，显式应用时保留原字节备份；旧案例、方法 ID、快照与批准历史不重写。开发和测试只用临时库及假模型，不修改正式学习库或调用真实媒体生成。
- 旧创作 Run 缺少完整 pin 时，只用经哈希核对的历史库备份恢复原上下文；找不到原库不得静默装载新版方法。学习提案的 `no_change` 与实际操作互斥。模型观察的声画种类、采样和音轨覆盖由保存的原分析决定，不能由提案扩大。
- 新案例的资源 ID 只能解析为本数据根内准确 Run、素材名及字节指纹；原片变化时拒绝回看，不用同名文件替代。学习 Agent 的历史观察按来源或游标有界读取；人类审阅用完整提案，模型只读不含整库差异的摘要，holdout 内容不能从迁移 diff 旁路进入模型。
- 偏好仅按明确的用户、品牌或项目身份和批准范围回流创作；范围不匹配时不加载，也不把个人喜好当成市场规律或审核结论。尚无可核对身份的偏好只存档，不声称已生效。
