## 2026-09-26 设计与验收记录

以下历史决定、验收及调用数据保留供追溯；现行局部修订交付不再调用独立审核。

### 背景与目标

现有 `plan_revision` 已约束用户原话、准确版本和字段，`Dispatcher` 也按阶段选责任角色；但任务目标、允许工具、预期产物和角色实际看到的来源分散在运行代码与模型请求中。排查一次修改为何改变作品、用了哪版依据时，需要从多个记录倒查。目标是在不增加模型调用、不改变审批与生成授权的前提下，让每次派工有可追溯的执行边界。

## 决定

沿用单进程 Python Harness、原 Pipeline、不可变产物和 run 事件日志。派工启动原 attempt 后，装配一次角色上下文：当前事实与用户实际选择、可读上游准确版本、需修改的旧稿及绑定审核问题、方法快照。生成不含正文的任务记录，绑定 attempt、阶段、责任角色、修订 plan、基线与输入指纹、可调用工具、预期产物和后续审核要求；记录来源版本与最终模型输入的指纹。模型仍只收到对应角色的独立上下文，动态工具读取仍以现有请求快照和产物证据记录。

脚本局部修改沿现有 `plan_revision → writer submit_patch → reviewer` 路径；任务契约不绕过 `check_base`、`patch_payload`、Pipeline 或用户对准确版本的决定。主制片可以选择和派发任务，但任务是否完成由程序核对新版本及独立审核。

第二步增加准确脚本字段的显式「直接修改」入口：页面把当前版本、指纹、字段路径及可见原句交给服务端重新校验；通过后沿上述任务路径执行，不占用主制片的自由对话上下文。普通发送保持讨论入口，不能仅凭选中文字推断用户授权改稿。旧稿无法无损局部修改、路径不唯一或附件会改变依据时拒绝定向执行，由用户在对话中说明范围。

## 取舍与失效处理

- 增加少量任务元数据与上下文哈希，换取版本和来源的直接追溯；不复制完整 Prompt 或素材到事件日志。
- 仍需主制片理解自然语言、选择字段。契约只限制执行，不证明它正确理解创意意图；真实模型质量另行验收。
- 构建上下文或模型调用失败时，原 attempt 按现有逻辑关闭，旧版本不变；已准备的任务记录不能冒充已交付。
- 不新建常驻 Agent、消息总线或 Rust 服务。未来其他任务类型可复用同一装配入口，但不因此自动迁移媒体链路。

## 验收

用离线假模型走完一次脚本局部修订：仅 `writer` 获得补丁工具，任务记录能定位计划、准确旧稿、上游来源与方法快照，未列字段和用户已选方向保持不变；新版需要独立审核，旧批准不继承。基线变化和失败不得生成新版本。真实模型与媒体生成不在本轮验收范围。

2026-09-26 隔离浏览器验收：在 Git 外临时数据根用假模型从实际页面选中第一段台词、提交定向任务，服务端只更新该字段并运行独立审核，未选中的第二段保持原文，新版无继承批准。另由同一隔离服务先推进版本后从旧页面提交，服务端返回 409；页面保留输入、清除旧目标并提示重新选择。该验证确认页面和本机 HTTP 链路，不代表真实模型的修改质量或实际费用。

任务结果进一步明确拆成两件事实：局部新版保存后立即在原 Job 进度日志记 `revision_result`（版本、指纹、`change_status=saved`、`review_status=pending`）；独立审核确有结论后追加同类型记录，将审核状态更新为 `pass` 或 `return`。Job 查询从完整事件流折叠最新记录，即使页面只请求增量进度仍可看到准确结果。整稿 `deliverable` 和 Job 状态继续独立判定；审核调用失败时 Job 仍为 `failed`，但用户能看到新版已保存且审核未完成。旧 Job 无此记录时，仅针对已有完整修订交付记录兼容旧页面显示。此记录只含阶段、版本和指纹，不含脚本正文或凭据。
