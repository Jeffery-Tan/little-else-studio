# 按问题执行与局部修订

本轮对应四点能力优化中的第 3 点：把用户修改交给责任角色，保留未受影响内容，并依据真实依赖决定后续工作。仅 US；实现仍使用原 Pipeline、角色循环、不可变版本和事件日志，没有新任务数据库或额外 Agent。下文含 2026-09-28 前的审核验收记录；新任务只由责任角色和主制片自检并交用户决定，历史审核结论不作门禁。

## 用户可见行为

| 用户要求或当前问题 | 执行方式 | 保留与后续处理 |
| --- | --- | --- |
| 只改第一句台词 | 主制片绑定当前脚本与该句字段，编剧只返回补丁 | 其他镜头、方向选择、素材安排不变；新版完整脚本重新内部审核，等待采用 |
| 调整一个镜头画面 | 绑定对应画面字段；需要联动的声音/台词须在范围中列明 | 未列出的字段不由模型重写；范围不足时说明具体关联问题 |
| 调整时码或时长 | 修改指定字段，程序把总时长标为待复核 | 仍须复查全片时长、衔接和节奏，不能把字段合法当作内容成立 |
| 审核发现素材计划缺少证据镜头 | 工作计划读取指向准确上游版本的责任问题，先交素材统筹 | 已有效的需求和方向保留；更新后脚本按新素材计划复核 |
| 商品证据更新 | 依据原指纹计算失效，按依赖顺序更新责任阶段 | 旧稿提供修订基线；需要重新采用的方向/脚本仍等用户决定 |
| 查看状态、暂停、反馈 | 只读工作计划/状态 | 不派工、不产生修订版本 |

这些行为已用离线模型验证。自然语言理解、选择哪个字段、修改后的创意质量仍由模型判断，尚未通过真实业务模型验收。

## 内部执行契约

1. `read_work_plan` 从原状态派生每阶段的 `preserve/create/update/revise/review/user_decision/recover/integrity_check`，列出真实阻碍及责任审核来源。没有用字段数量或文件存在判定内容通过。指定 target 只限制下一步的搜索范围，不隐藏其他阶段状态。
2. 对话 edit 路由修改已有阶段前，`plan_revision` 绑定本轮用户原话、阶段、版本、完整指纹与输入指纹。主制片决定 local/rework 并说明原因；用户不需要填写路径或派工参数。原话包含校验不能证明模型正确理解了用户意思。
3. local 列明已有字符串字段的路径、修改要求及基线值；只支持结构生成的正文。不能删除/新增/重排整行、替换整个对象、改方向 key 或修改未列字段。同轮不能把 local 扩大成其他阶段或全文重写。
4. 专业角色的实际工具集合移除 `submit_stage`，开放 `submit_patch`；运行循环按实际集合拦截越权调用。补丁先完整校验，再由程序合成新结构和正文。其他字段、顺序、旧证据与限制保留；新增实际方法引用仍记录。主制片的 intake 补丁沿用同一校验，不再调用子角色。
5. 全文重审需求使用 rework，提供准确旧稿、变化的输入来源、当前商品观察和真实选择。计划本身不会运行模型或改产物；派工仍走原一次任务、费用与停止机制。
6. 模型前与提交前重新检查基线和依赖。过期、越界、空变化、取消均不创建新版本；未提交的角色任务按原机制关闭。任务完成后派工结果返回当前工作计划。
7. `agent_revision_planned` / `agent_revision_applied` 追加到原 run 的事件日志。计划只在当前对话轮持有，新消息不能复用旧 plan_id；事件供追溯，不构成权限恢复。

这一实现沿用 [dsh 工具能力与执行控制分离](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45fbc7f8e46dd73185e68295696d1297887/docs/architecture.md) 的思路：模型解释工作，程序限定实际可执行范围。没有引入 dsh 依赖或替换 Python 运行时。

## 明确边界

- 现有阶段依赖仍是完整产物指纹。例如方向的新版本会让已有素材计划和脚本失效，即使只改了一个方向字段。这里没有声称已经做到字段级下游批准复用；审批继续绑定用户实际看过的完整版本。
- 商品素材或观察摘要变化继续按原证据快照保守失效。不会因为一句话没变就把证据变化忽略；也不会自动确认模型观察。
- 旧正文与卡片分别保存的版本不支持保证无损的局部补丁，明确返回原因。已有界面编辑兼容流程保留；不得静默换成全文生成。
- 局部修改仍需复查全片表达。文字审核没有变成视频看听，不把此项实现计作第 4 点成片验收。
- 没有开放图片/视频生成、审批、费用授权或发布工具。此次没有更新真实运行环境、重启业务服务或调用真实模型。
