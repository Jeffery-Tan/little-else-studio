# 制片交互架构

本契约服务于创作者理解当前结果、阻碍与下一步。项目进展、后台任务和用量是三个不同概念；任务执行结束不代表方案通过审核或被用户采用。

## 默认用户旅程（对话优先）

1. 首页输入一句话，可同时附图片/视频。发送自动建立项目；项目名、运行 ID、内部阶段不需要填表。
2. 主制片同一轮理解意图、调用视觉能力检查已提供的商品图、形成并内部审核具体创意方向，给出开场、推进和推荐。需求整理是中间步骤，不以建议下轮派工结束。只有影响创作的关键歧义需要澄清时用 `ask_user` 提供一个问题、推荐选项和自由补充，持久化后停止本轮，等待用户回答。
3. 同一工作区先显示当前创意，旁边保持对话。待选与已采用的方向都以作品卡呈现；用户在准确版本上采用后，系统接续素材安排与脚本策划。内部派工和审核由团队处理。若方向推荐项与当前 **ActiveBrief** 不一致（`brief_gate=blocked`），决定卡只提供「批准修订简报」或「按原简报退回重做」，不提供 A/B/C 硬过；修订批准后本版作废、团队按新简报重做。
4. 脚本按实际表达显示画面与动作、声音、台词或图内文案，并保留准确版本的就地决定。空台词字段不被推断为刻意无口播；没有成图时使用已保存的准确画面描述。确认后主制片准备分镜图的制作输入，并使用冻结的审核模型完成文字检查；用户核对内容和费用后提交图片生成。
5. 分镜与成片是同一画布的两个视图。分镜图须在大图中实际展示并由用户确认；明确的视频项目确认图片后，以图像及已确认脚本的准确 SHA 和固定请求标识发起原主制片任务，准备视频输入和独立文字检查。任务未能启动时显示原因，用户可显式继续；生成仍须另行核对范围与费用并授权。顶部准备动作一次点击发起团队任务，已保存方案若模型能力不可用则指向模型设置。制作受阻时用户可针对准确制作稿在对话中说明问题；手工参数表收在高级入口。新尝试失败或结果待核实，上一份仍有效的生成结果继续可看，本次状态与原任务恢复单独呈现。

普通问答不是正式批准。`interaction_requested/interaction_answered` 写入原事件流，不建立第二套问答数据库。问题恢复会带回原选项；旧问题 ID 不能回答新问题；回答重试复用任务 request_id。采用、图审和生成继续使用原有准确内容绑定与浏览器确认。

首轮项目创建通过 `/api/conversations` 将 request_id 确定性地映射到一个项目，同身份不同内容拒绝覆盖。附件完整上传后才发送首轮任务；附件重试必须与原字节哈希相同。首轮请求未确认时保留身份，不能重复创建或重复调用模型。

后台仍以四阶段产物、审核记录及审批维护依赖。默认页面按最终交付、当前创意或脚本、实际图片或视频及主要动作组织；原始需求、版本、制作描述和尝试记录按需打开。旧项目原文及批准不自动迁移或改写。

同一创作项目中临时只分析新参考时，顶部保留原项目最终交付，将本轮参考报告作为当前任务优先展示；分析报告不会自动成为制作依据或触发生成。

现有视频提供方仍是单首帧生成。本次交互改造不代表已经支持多图同时约束、多段自动剪辑、连续镜头一致性或真实生成质量验收。浏览器交互使用独立临时目录与假模型验证，真实项目仅只读检查。

## 状态只投影，不另建事实源

`studio/project_brief.py` 从既有 pipeline 状态、不可变产物和任务事件计算后台项目摘要。前端的只读创作者视图再结合现有 timeline、制作与参考任务读接口，决定默认展示哪个作品和下一动作；它不持久化第二套状态，也不改变领域层的批准、版本或任务门禁。用量记录不决定能否继续创作。

## 主制片承担协调

每项问题明确 `owner=user|team`、`timing=now|later`、`reason` 和 `kind`（`fact` / `product_choice` / `local_design` / `brief_amendment`）。只有当前阶段明确属于用户、现在需要回答、**非 `brief_amendment`** 且有原因的问题进入用户待办。要改产品目标/有效简报的问题不走普通问答，走简报修订门禁。文件检查、版本关联、模型能力判断、审核归纳由团队承担。旧稿未标明责任的问题保留在团队待整理事项中，不表示问题已经解决。

用户提供的使用场景与偏好不能自动升级成市场事实或必须逐一演出的情节。审核发现先由主制片合并同类原因，完成能自行解决的工作，再说明真正需要用户决定的事项。

## 正文与创作板共用内容

新结构化产物使用 `content=""` 加完整 `structured` 提交，由确定性渲染器生成正文。拒绝会被截断或丢弃的源字段。正文与创作板共用同一份内容；支持的单元格修改在本地同步两者并生成新版本，不额外调用模型改写。

旧稿保留原文、版本与哈希。不能确定正文完全来自结构化渲染器时，仍使用原来的受控修改流程，不做静默迁移。

## 操作绑定准确版本

“审核这一版”调用专用 `/actions/review` 命令，绑定 request_id、版本及 SHA256。执行前再次检查版本、开放尝试和审核条件，直接调用独立审核角色；保存审核结论即完成操作。失败只提供该版审核重试，不隐式重写方向。审核通过仍需要用户明确采用。

原有任务管理器继续负责幂等、并发和取消。重复请求不会产生新任务；旧页面不能操作已经变化的稿件。真实生成和参考图审批保持各自的明确授权。

## 对话是结论，工作记录是过程

工具执行前后的叙述记录为活动事件；最后的助手回复只保留最终答复。每轮成果链接绑定当轮实际版本。长篇历史回复与工作记录可展开阅读，不覆盖旧记录或伪造摘要。桌面同时展示创作板与对话，窄屏切换完整阅读区域，共用顶部项目状态。

项目顶部持续显示当前结果，即使当前作品或决定卡已经打开；可执行的下一动作只出现一次。审核未通过时，决定卡默认展开具体意见，以「退回并继续修改」为主操作，具名覆盖审核保留为次要操作；通过审核时维持采用入口。审核类型只用人能理解的标签呈现，原始类型可留在技术记录中。

下一轮以全新项目的一条完整任务链验收：从首页输入需求开始，创建后先看见已保存的目标、最新结果和唯一待办；点进方向或脚本时先获得可比较的概要，再按需展开证据与全文；给具体字段提意见时始终看得见选中的原句和将发生的动作；做决定前同时看见本版内容、审核理由及决定后果；提交后立即回到新状态与准确版本。角色分工、上下文来源、工具调用和用量继续保留可追溯入口，但不挤占创作者的主阅读区。先用隔离新项目与合成阶段状态覆盖首次发送、方向选择、审核退回、字段修改、执行中和结果未知；旧项目备份及旧稿迁移不作为本轮交互验收前提。真实模型和媒体生成另按实际调用、图审及费用门禁验收。

## 验证边界

离线回归覆盖状态投影、事项归属、版本绑定、审核失败恢复、幂等、无模型局部修改及正文一致性。浏览器验证真实项目的导航、可读性与控制台。旧创意内容不因 UI 更新而改变；新的表达质量与真实模型响应速度仍需后续实际使用检验，不能用离线成功替代。
