# 制片交互架构

本契约服务于创作者理解当前结果、阻碍与下一步。项目进展、后台任务和用量是三个不同概念；任务执行结束不代表方案通过审核或被用户采用。

## 默认用户旅程（对话优先）

1. 首页输入一句话，可同时附图片/视频。发送自动建立项目；项目名、运行 ID、内部阶段不需要填表。侧栏「开始创作」只负责返回这个输入框；空工作台不再显示第二张新建项目卡，已有项目列表只用于继续和搜索，回收站固定在侧栏。
2. 主制片同一轮理解意图、调用视觉能力检查已提供的商品图、形成并内部审核可比较的创意方向，给出简短开场识别点、推进概念、取舍和推荐。方向待选时不提前写台词、逐镜头或逐页脚本。需求整理是中间步骤，不以建议下轮派工结束。只有影响创作的关键歧义需要澄清时用 `ask_user` 提供一个问题、推荐选项和自由补充，持久化后停止本轮，等待用户回答。点选答案只填入对话框，用户可补充或改写；明确发送后才创建下一轮任务，并携带原问题 ID 防止过期选项回答新问题。
3. 同一工作区只展示当前创意成果，旁边保持对话。方向、脚本的选择、修改意见、澄清和继续推进都在对话区完成；画布中的作品卡不提供决定表单。后台仍以准确版本和指纹绑定决定，但主界面不罗列历史版本。对话使用用户可理解的阶段名称，不展示 `intake-v1` 等内部稿件标识。内部派工和审核由团队处理。若方向推荐项与当前 **ActiveBrief** 不一致（`brief_gate=blocked`），该方向只能作为修改参考，不能直接采用；修订简报须另经明确批准，修订后本版作废、团队按新简报重做。简报修订批准只采用卡片展示的具体正文；用户填写进一步修改意见时须退回要求新版，不把备注当作已经写入简报的条件。
   方向稿已保存但审核未完成时，主要下一动作始终是审核；其他待确认事项单独列出。素材方案中标为阻塞的关键缺口须先解决或重做方案，编剧不在缺口尚存时继续写完整脚本。对话里的阶段结论依据已保存产物和真实审核状态生成，不由模型自行宣布可采用。
4. 脚本按实际表达显示画面与动作、声音、台词或图内文案，决定在对话区完成。空台词字段不被推断为刻意无口播；没有成图时使用已保存的准确画面描述。确认后主制片准备分镜图的制作输入，并使用冻结的审核模型完成文字检查；用户从对话区进入准确输入、范围与费用核对后提交图片生成。
5. 分镜与成片是同一画布的两个只读成果视图。图片和视频的当前结果在画布展示；继续制作入口在对话区，准确图审与费用授权使用独立核对弹窗，不在画布叠加按钮。明确的视频项目确认图片后，以图像及已确认脚本的准确 SHA 和固定请求标识发起原主制片任务，准备视频输入和独立文字检查。任务未能启动时显示原因，用户可显式继续；生成仍须另行核对范围与费用并授权。已保存方案若模型能力不可用则指向模型设置。制作受阻时用户可针对准确制作稿在对话中说明问题；手工参数表收在高级入口。新尝试失败或结果待核实，上一份仍有效的生成结果继续可看，本次状态与原任务恢复单独呈现。

普通问答不是正式批准。`interaction_requested/interaction_answered` 写入原事件流，不建立第二套问答数据库。问题恢复会带回原选项；旧问题 ID 不能回答新问题；回答重试复用任务 request_id。采用、图审和生成继续使用原有准确内容绑定与浏览器确认。

首轮项目创建通过 `/api/conversations` 将 request_id 确定性地映射到一个项目，同身份不同内容拒绝覆盖。附件完整上传后才发送首轮任务；附件重试必须与原字节哈希相同。首轮请求未确认时保留身份，不能重复创建或重复调用模型。

后台仍以四阶段产物、审核记录及审批维护依赖。默认页面按最终交付、当前创意或脚本、实际图片或视频及主要动作组织；原始需求、版本、制作描述和尝试记录按需打开。旧项目原文及批准不自动迁移或改写。

同一创作项目中临时只分析新参考时，顶部保留原项目最终交付，将本轮参考报告作为当前任务优先展示；分析报告不会自动成为制作依据或触发生成。

现有视频提供方仍是单首帧生成。本次交互改造不代表已经支持多图同时约束、多段自动剪辑、连续镜头一致性或真实生成质量验收。浏览器交互使用独立临时目录与假模型验证，真实项目仅只读检查。

## 状态只投影，不另建事实源

`studio/project_brief.py` 从既有 pipeline 状态、不可变产物和任务事件计算后台项目摘要。前端的只读创作者视图再结合现有 timeline、制作与参考任务读接口，决定默认展示哪个作品和下一动作；它不持久化第二套状态，也不改变领域层的批准、版本或任务门禁。用量记录不决定能否继续创作。

## 主制片承担协调

每项问题明确 `owner=user|team`、`timing=now|later`、`reason` 和 `kind`（`fact` / `product_choice` / `local_design` / `brief_amendment`）。只有当前阶段明确属于用户、现在需要回答、**非 `brief_amendment`** 且有原因的问题进入用户待办。要改产品目标/有效简报的问题不走普通问答，走简报修订门禁。文件检查、版本关联、模型能力判断、审核归纳由团队承担。旧稿未标明责任的问题保留在团队待整理事项中，不表示问题已经解决。

用户提供的使用场景与偏好不能自动升级成市场事实或必须逐一演出的情节。审核发现先由主制片合并同类原因，完成能自行解决的工作，再说明真正需要用户决定的事项。

## 正文与创作板共用内容

新结构化产物使用 `content=""` 加完整 `structured` 提交，由确定性渲染器生成正文。拒绝会被截断或丢弃的源字段。正文与创作板共用同一份内容；支持的单元格修改在本地同步两者并生成新版本，不额外调用模型改写。

旧稿保留原文、版本与哈希。不能确定正文完全来自结构化渲染器时，仍使用原来的受控修改流程，不做静默迁移。

## 操作绑定准确版本

“审核这一版”调用专用 `/actions/review` 命令，绑定 request_id、版本及 SHA256。执行前再次检查版本、开放尝试和审核条件，直接调用独立审核角色；保存审核结论即完成操作。失败只提供该版审核重试，不隐式重写方向。审核通过仍需要用户明确采用。

原有任务管理器继续负责幂等、并发和取消。重复请求不会产生新任务；旧页面不能操作已经变化的稿件。真实生成和参考图审批保持各自的明确授权。

## 对话是结论，工作记录是过程

工具执行前后的叙述记录为活动事件；最后的助手回复只保留最终答复。每轮成果链接绑定当轮实际版本。长篇历史回复与工作记录可展开阅读，不覆盖旧记录或伪造摘要。桌面同时展示创作板与对话，窄屏切换完整阅读区域。

当前进展放在对话中；项目顶部只保留未在当前画布出现的下一动作，项目与设置位于标题栏右侧。运行中的任务由输入框原发送按钮执行「停止」，停止期间禁用按钮；输入框中的草稿不随停止丢失。审核未通过时，决定卡默认展开具体意见，以「按意见修改，先出新版」为主操作；具名覆盖审核收在单独入口，使用独立理由输入框，不能把尚未处理的修改意见当成覆盖理由。通过审核时仍可明确采用当前版。审核类型只用人能理解的标签呈现，原始类型可留在技术记录中。

## 验证边界

离线回归覆盖状态投影、事项归属、版本绑定、审核失败恢复、幂等、无模型局部修改及正文一致性。浏览器验证真实项目的导航、可读性与控制台。旧创意内容不因 UI 更新而改变；新的表达质量与真实模型响应速度仍需后续实际使用检验，不能用离线成功替代。
