# 对话交互与用户指令控制审计

审计及实施日期：2026-10-03。首次审计基线为 `6176292` 及当时已有工作树改动。本文保留修复前问题与同日实施、复审记录；开头问题描述属于历史基线。最新修复证据见[九处缺口的修复与复验](#九处缺口的修复与复验2026-10-03)，当前能力、服务加载及剩余验收统一见[实现与验收状态](product-improvements.md)。架构研究来源见 [DeepSeek Harness 复核](deepseek-harness-review-20261003.md)。

## 初始审计结论与证据范围（修复前）

当前最需要修复的是用户输入在不同入口之间的身份、范围与处理状态。同一句话会因任务忙闲、是否选中作品、是否点击直接修改而获得不同效力；系统能够核验产物版本，却还不能可靠保证「只讨论」「只改一句」「采用但带条件」贯穿整个执行过程。这足以造成用户感受到的无响应、意见没被落实、停止和继续不符合预期。

本次沿输入框、HTTP 入站、运行中消息、决定服务、主制片、角色任务及返回状态逐层核对。证据分三类：

- **离线行为复现**：真实前端函数加已有 fake DOM；真实 ASGI 路由、JobManager、Orchestrator、Store 和决定服务加临时数据及假模型。假模型仅提供确定的返回值，没有调用真实模型或媒体服务。
- **边界反例**：故意给服务一个错误的模型候选，检查它会不会被接受。这证明拦截能力有缺口，不证明线上模型已发生同样误判。
- **静态确认**：检查上下文组装和权限路径，尚未通过真实模型统计发生率。

首次审计时没有修改应用实现、现有测试、运行数据或服务，没有重启、生成、提交付费请求；已有工作树改动均保留。当时本地浏览器访问受策略限制，未验证实际运行页面加载的代码指纹、视觉表现或具体历史项目；以下结论针对当前仓库实现，不把离线复现冒充线上事故追踪。

优先级：P1 为应在继续扩大 Agent 能力前修复的控制缺口；P2 为明确的交互缺陷。本次不将可逆创作状态问题标成已发生的付费越权。

## 已确认的问题

### F1 · P1：运行中收到的真实用户消息，在接续时丢失用户身份

**触发**：团队工作时发送「采用 B」。

普通 `/jobs` 先记录 `user_message_received`，保存原话和展示凭据，再给执行器传 `user_input_id`。运行中 `/steer` 只保存 `job_steer_received`。旧轮结束后，`jobs.py` 把旧要求和补充拼成文字，创建没有 `user_input_id` 的接续任务。执行器因此标为 `internal_instruction=True`，决定工具随即拒绝批准。

真实 HTTP/JobManager 离线复现结果：HTTP 200；原话进入 steer 事件；没有对应用户消息凭据；接续被标为内部指令；假模型正确提出 B 后，真实工具返回「没有新的真实用户决定」；批准记录数量为 0。假模型共调用 3 次，均为内存函数。

**影响**：用户已经表达的决定不能在忙时正常生效，可能需要重复说；待答问题的忙时回复也经过内部路径，`interactions.answer` 在该路径被跳过，后者为静态确认。

**证据**：`studio/http_execution.py:182`、`:267`；`studio/jobs.py:523`；`studio/server.py:234`；`studio/agents/orchestrator.py:157`、`:169`、`:703`。

**修复边界**：空闲、运行中和重新接续共用真实消息入站，保留每条原话、独立 message ID、展示对象及消费状态。程序派生说明仍属于内部消息；不能通过放宽内部消息批准权限来修这个问题。多条补充保留各自身份，不合并成一个虚构用户决定。

### F2 · P1：中途意图分类会把否定的停止指令反着执行

直接调用当前 `steer_intent.classify` 的结果：

| 用户原话 | 当前分类 | 对调度的实际含义 |
| --- | --- | --- |
| 现在进度怎么样？ | status | 不取消原轮，但存在 F3 |
| 生成完了吗 | work | 要求原轮结束，再尝试启动接续 |
| 不要停止当前任务 | stop | 取消原轮，丢弃待接续调整 |
| 别取消任务，我只是问进度 | stop | 同上，否定关系被反转 |
| 暂停 | work | 原轮结束后仍尝试接续 |
| 先别做了，等我确认 | work | 同上，等待要求未在调度层成立 |
| 只讨论一下，先不要改 | work | 会中断并接续；讨论的只读边界另见 F5 |
| 这次先不用生成了 | work | 结束原轮后仍尝试接续 |
| 停 | stop | 正确停止，不自动接续 |

原因是先匹配未排除否定的「停止/取消…任务」子串，再用包含「生成」「不要」等词的列表排除 status，其余全部当 work。它在 Agent 理解原话之前就决定取消与接续。

**影响**：用户只是问完成没有，也可能中断工作；用户要等待，也可能启动额外模型轮次。这里不等于已证实远端视频被重新提交或多扣费，供应商任务与本地对话的生命周期要分别处理。

**证据**：`studio/steer_intent.py:40`、`:84`、`:109`；`studio/jobs.py:370`、`:406`、`:514`。

**修复边界**：把「说的是什么」「何时消费这条消息」「是否取消当前工作」分开。询问不取消；明确停止取消并丢弃待执行调整；普通补充进入下一安全步骤；含否定、条件或歧义的消息不能仅靠命中一个子串就取消或自动续跑。不要用继续堆短语替代上述边界。

### F3 · P1：进度问句未进入 Agent 输入，也可以被标成已回答

运行中发送「现在进度怎么样？」，服务立即承诺「主制片会在本轮结束前回答当前真实进展」。但 status 消息只进 steer 事件，没有注入已执行中的模型输入，也不产生新回答。原轮结束时直接记录 `job_steer_answered`。

真实 HTTP 离线复现：原任务的假模型被阻塞；发送进度问题后释放原任务；原任务只返回固定无关答复。最终 `steer_status=answered`，模型调用数为 1，问题既未进入模型请求，也未进入普通 chat，没有该问题的用户凭据。

**影响**：「已收到」「已回答」与实际处理脱节，用户无法区分系统看到了消息还是已经处理了要求。

**证据**：`studio/jobs.py:392`、`:397`、`:506`；`tests/test_jobs.py:95` 的现有用例主要检查不取消和不接续，没有要求生成与问题对应的回答。

**修复边界**：简单状态问句可以直接读取同一份任务/制作状态投影并生成明确回复，不必增加模型调用；需要 Agent 判断的问题要真正投递，并以关联的回答事件确认完成。没有回答证据，只能显示已收到或待回答。

### F4 · P1：运行中点击「按意见直接修改」，专用修改命令被降成普通补充

选中脚本的一句口播并点击直接修改，空闲时发 `request_kind=writing_revision`，走绑定字段的 `/actions/revise-writing`；忙时 `send` 提前走 `/steer`，只带 text、目标和 revision，丢掉 `request_kind`。

真实前端函数离线复现：`submit('writing_revision')` 返回 accepted；捕获到的是普通 steer payload，字段目标仍在，但没有直接修改的命令种类。

**影响**：用户点击的明确操作被交还给主制片重新解释。不能据此断言必然改错字段，但专用执行路径提供的约束确实没有沿用。

**证据**：`studio/web/app.js:553`、`:1960`；`studio/web/runtime.js:708`。

**修复边界**：明确按钮操作是带类型的命令，运行状态只能改变排队时机，不能改变命令含义。若暂不能排队，清楚说明并保留整份输入；处理时重新核验原字段、版本及依赖，过期则拒绝，不能悄悄指向新版。

### F5 · P1：首次工作范围和交付目标主要由模型自己声明

本轮 `_scope_selected` 初始为 false，第一次 `prepare_creative_context` 接受模型自报 intent/format。代码能阻止已经选为 status/pause 后再升级，却没有独立的本轮约束来校验首次选择。`deliverable` 不是必填；缺省时完成检查直接跳过，`follow_up` 也按信息回复处理。

局部修改还有同类缺口：真实 `plan_revision` 传入用户原话「只把第一句改得自然一点，其他内容保留」，第一次计划设为 `mode=rework, fields=[]`，服务接受。已有 local 计划之后禁止扩范围，不能解决第一次就选错范围。

**影响**：状态/讨论可能被错误路由成创作；局部修改可能先被解释成整稿重做；明确交付可能被缩成一段聊天回复。前两项中，局部计划接受 rework 已离线复现；自由文本首次误路由、错误交付类别为可达路径，尚未测量真实模型的发生率。

**证据**：`studio/agents/orchestrator.py:179`、`:458`、`:758`、`:936`；`studio/tools/registry.py:190`；`studio/task_contract.py:93`；`studio/revision_scope.py:137`。

**修复边界**：服务端持有本轮任务解释，至少包含原消息来源、动作种类、具体交付、允许修改范围、必须保留的内容和执行方式。明确 UI 命令直接确定边界；自由文本仍可由模型解析，但解析是可验证、可澄清的候选，执行工具不能自行改写约定。未知交付不应报「完成具体成果」。已有准确字段 patch 和产物版本机制继续使用。

### F6 · P1：版本和选项校验正确，仍可能接受没有采用意图的模型候选

临时项目展示了 A/B/C，用户原话为「我现在在读 B 方案的详细内容」。故意向真实决定服务提供 `select_direction B` 候选，`resolve` 返回 commit，`commit` 写入 approved B，派生「我已采用…继续完成素材安排和完整方案」。

这是**错误模型候选的边界反例**。没有用真实模型证明这句话会被误读。`validate_proposal` 自己也明确说明它不是一般自然语言证明：它拒绝部分假设、引用、问题和否定表达，但较长陈述带 B 且未命中排除规则时仍可能通过。

**影响**：状态唯一提供某动作、用户明确提到 B，只能证明对象可定位，不能证明用户采用了 B。

**证据**：`studio/conversation_input.py:95`；`studio/decision.py:361`、`:469`。

**修复边界**：任务解释须区别陈述、比较、提问、修改与决定，并保留支持决定的完整原话及未决条件；明确无歧义的可逆决定仍可自然语言生效，含糊的只澄清一次。建立陈述、否定、引用、条件句等反例集。不能声称新增一个分类模型或关键词检查即可完全证明用户意图，也无需把所有自然决定改成额外点击。

### F7 · P1：用户的附加条件没有被保证传到接续和专业角色

原话「采用 B，但开头更生活化一些，然后继续」，模型只提出 B，漏填 `continuation_note`。真实服务接受批准，保存的 note 为空，派生指令没有「开头更生活化」。

原话仍留在聊天中，主制片近期上下文可能再读到，所以这不等于文本彻底丢失。但普通角色任务由主制片填写 brief；任务组装器自动加的是必要产物、方法和修订范围，没有自动附入本轮完整原话或相关未落实约束。导演有 ActiveBrief 的已确认条件，其他角色主要从产物和 brief 继承。

**影响**：用户以为条件已经明确，跨轮或换角色后仍可能遗漏。保存 prompt 的 hash 能证明实际发过什么，无法证明该发的条件都已传齐。

**证据**：`studio/decision.py:419`、`:475`、`:574`；`studio/agents/orchestrator.py:1012`；`studio/task_context.py:33`、`:98`；`studio/tools/dispatch.py:267`。

**修复边界**：任务引用完整原消息，并抽取带来源、适用对象和状态的约束，相关角色上下文自动组装；交付核对这些约束。方向选择和后续修改拆成有关联的动作，分清条件作用于已采用方向还是后续脚本。项目长期条件与本轮临时要求分开；后续明确纠正可以替换旧约束，不能无限累加相冲突要求。继续保持角色上下文隔离，不向每个角色灌全部聊天。

### F8 · P1：切换项目保留了反馈文字，却清除了反馈对象

绑定一张图片，输入「这张图的肩带改短一点」，切到别的项目再返回。`selectRun` 按项目保留文本，却无条件 `clearFeedbackTarget()`。

离线复现：返回后 draft 原样存在、target=null；继续发送只带文本和 request_id，没有 attempt、图片指纹或准确版本。

**影响**：「这张图」「这一句」失去指代，Agent 只能重新猜用户想改哪份内容。旧目标过期时需要重新确认，但不能静默抹掉绑定后仍允许作为同一反馈发送。

**证据**：`studio/web/app.js:184`、`:197`、`:437`、`:2003`。

**修复边界**：每个项目保存整份输入草稿，包括文本、目标、命令和附件。返回时验证原目标；有效则恢复，过期则提示重新选择并保留原话。

### F9 · P1：附件上传后对话被明确拒绝，再发会丢失附件用途

附上 reference.mp4，用途选「参考视频」，发送「学一下这个节奏」。上传成功后立即清空 composer 的附件；若随后创建任务得到明确拒绝，只恢复上传前的原始文字。

离线复现的两次请求内容：第一次为「学一下这个节奏\n本次附上的素材：reference.mp4（参考视频，用于拆解表达）」；重试只剩「学一下这个节奏」，附件列表为空。

**影响**：文件仍在项目中，但本条请求不再明确关联文件和用途。商品资料与创作参考在该产品中有不同含义，不能让 Agent 根据文件名或历史猜。

**证据**：`studio/web/app.js:1998`、`:2092`；`studio/web/conversation-input.js:16`。

**修复边界**：文件上传状态与消息是否接受分开；已上传附件保留稳定引用及用途，收到明确拒绝后恢复整个输入。不得为了恢复草稿再次上传同名文件。现有「提交结果未知时冻结原 payload、按同一 ID 查询」机制正确，应继续保留。

### F10 · P2：排队或停止中的「发送」按钮可点，但会静默返回

`syncComposerAction` 在活动任务状态展示并启用副按钮「发送 ↑」。`submit` 对不能 steer 的活动任务直接 return；点击处理器丢弃返回原因，没有提示。

真实 runtime 和 app 函数离线复现 queued 状态：按钮可见、enabled=true、label=发送 ↑；点击后 POST 数量为 0，toast 为空，文本仍在。cancelling 的不可插入分支受同一条件影响。queued 的返回理由还错误写成「正在停止」。

**证据**：`studio/web/runtime.js:208`；`studio/web/app.js:2072`、`:2132`。

**修复边界**：可发送就实际接收并显示排队状态；不可发送就禁用并说明当前原因。点击和 Enter 共用结果反馈，任何拒绝都可见且保留草稿。

## 理想交互与工程边界

用户继续使用一个对话框，不需要记专用 prompt 格式或理解内部阶段。系统需要统一以下语义：

| 用户动作 | 应有表现 | 必须持有的边界 |
| --- | --- | --- |
| 问进度、问为什么 | 读取当前真实状态并回答；在途任务继续 | 回复关联本条问题，不把接收写成回答 |
| 只讨论、分析问题 | 可以阅读和解释，结束于分析 | 不改稿、不采用、不启动媒体提交 |
| 指向某图、某段、某句提意见 | 展示准确对象的引用；保留用户原话 | 目标版本、图片指纹或视频时间点不漂移 |
| 按意见直接修改 | 忙时排队，空闲时执行；改完展示差异 | 命令种类不变，局部范围程序约束 |
| 采用 B，但提出条件 | 明确记录选择与条件分别影响什么 | 决定对象、附加条件和接续意图分别保留 |
| 运行中补充或纠正 | 立即显示已收到，在安全步骤消费 | 保留真实消息身份；新要求只替换受影响部分 |
| 停止、等我确认 | 停止可取消工作，旧调整不自动接续 | 外部已提交任务保留查询，不自动重提 |
| 继续 | 恢复当前未完成目标，说明实际从哪继续 | 不放大原目标，不重新批准或自动收费 |
| 切项目、刷新、发送失败 | 能恢复完整草稿或原请求状态 | 文本、附件用途、对象和命令保持一致 |

推荐在既有入站和事件存储上形成一条可检查的链：

```text
用户原话 + 附件用途 + 准确对象 + 显式命令
                  │
                  ▼
统一入站：不可变 message_id / request_id / 原始来源
                  │
                  ▼
本轮任务解释：讨论/决定/修改、交付、范围、保留项、条件
                  │
           有歧义才澄清
                  ▼
调度：立即只读 / 下一安全步骤 / 下一轮 / 明确停止
                  │
                  ▼
主制片与专业角色：同一任务约束 + 各自必要上下文
                  │
                  ▼
领域工具校验 → 准确产物或回答 → 关联原消息的处理结果
```

以上是建议的契约，不增加第二套任务数据库、批准写入点或制作进度事实源。用户输入负责表达意图，模型负责解释和创作，程序负责对象、范围、权限、调度和完成证据。`received`、`queued`、`applied`、`answered` 等内部状态可细分；界面只需给出真实的「已收到、等待处理、正在修改、已完成、需补充」及具体原因。
